# Redaction pseudonym engine and leak-detection harness (T01 + T02)

Two staged tasks that build the detection apparatus and the naming core for EXPLAIN log redaction, with no user-visible surface. T01 adds a marker-based leak detector (`zsec_` on identifiers, `zsecdata-` on stored values) plus a 33-entry fixture catalog, asserting in the *positive* direction that today's unredacted EXPLAIN leaks everything — the assertions invert once T04 lands. T02 adds `RedactCtx`: three dynahash tables and per-kind counters living in the caller's memory context, two entry points (OID-keyed and position-keyed), a namespace-based exemption test, and an assert-build tripwire keyed on the T01 markers. I ran the T01 regression file, the T02 module test and the TAP file on this tree (cassert build, 24/24 TAP subtests, both regression files byte-identical to their expected output), which is why the findings below matter: everything green here is green partly for reasons that do not hold.

**Watch for:** `explain_redact_destroy()` hands the caller's own memory context to `hash_destroy()` three times, which deletes that context and then walks freed memory (confirmed; no caller, no coverage). Four more fixtures in the class the author already found twice — FR-16 "index name", FR-20 "user collation", FR-46 "subquery output name + alias", FR-93 "composite field assignment" — never reach the emission site they name and pass on incidental table and column names (confirmed by running them). Three auto_explain assertions are satisfied by the `Query Text` property before any plan property is consulted, and the libxml gate in `002_redact.pl` is always false, so FR-95 is skipped on every build including one with libxml (confirmed). `t/002_redact.pl` is missing from `contrib/auto_explain/meson.build`, so it never runs under meson (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The engine's memory model is "allocate in the caller's context, let the caller's reset free it", which is what the design asks for and which works. The exported `explain_redact_destroy()` contradicts it: dynahash frees a table by deleting its `hcxt`, and all three tables were handed `CurrentMemoryContext` at create time, so destroy deletes the caller's context and then dereferences the `RedactCtx` that lived in it. Nothing calls it today.

Returned pointers have two different owners depending on which branch produced them. A pseudonym points into a hash entry owned by the context the `RedactCtx` was created in; an exempt name is whatever `get_rel_name()` just palloc'd in the context current at call time. Once explain.c and ruleutils.c call this from short-lived per-node contexts, exempt names die earlier than pseudonyms — a difference keyed on catalog state rather than code path. The same branch palloc's a namespace name on every request, exempt or not, because the exemption test runs ahead of the cache lookup.

The `REDACT_COLUMN` recursion is safe: dynahash relinks buckets on expansion but never relocates elements, so the outer entry pointer survives the inner `HASH_ENTER`. The name it builds is the problem — it qualifies with the *alias* pseudonym, so columns always read `a1_c1`, never the `t1_c3` that the header, design §3 and FR-12 all specify, and the function as written has no path to that form. FR-41's well-formedness regex is applied to nine of the twenty kinds, and the composite column form would fail it.

The fixture catalog's positive control asserts that *some* marked identifier appeared, never which one. Printing the identifiers each fixture actually found exposes four whose named path contributes nothing: the index-name fixture gets a Seq Scan, the collation fixture loses its `COLLATE` to constant folding, the subquery fixture is flattened away, and the composite-assignment fixture's field name is not printed in any shape I could find.

The grep survives the thing most likely to break it — markers pass through JSON, XML and YAML escaping unchanged, verified in all four formats. Its blind spots are values that are not text (`numeric` and `timestamptz` columns cannot carry a marker, which is what makes the FR-98d fixture's value half unobservable) and case, which a marked identifier evades through `upper()`. Neither is exercised, and T01 runs text format exclusively against its own standing criterion of "any of the four formats".

On the log side, auto_explain emits `Query Text` in every record, so any assertion of the form "this identifier appears in the log" passes before the plan is examined; three are written that way. Separately, `$has_libxml` probes `pg_proc` for `xmlelement`, which is grammar and has no catalog row, so the FR-95 block skips unconditionally and the skip counts as a pass.

The exemption boundary is OID-compared for `pg_catalog` and string-compared for `information_schema` and the allowlist, which leaves the exempt set reachable by anyone who can rename a schema.

Registration is complete for the engine and the test module in both build systems; only the new TAP file is missing from the meson side. The regression test's placement in the `explain` parallel group is safe. One SQL-callable crash: a NULL array element reaches `TextDatumGetCString` unchecked.

## `explain_redact_destroy()` deletes the caller's memory context

`explain_redact_create()` records `ctx->cxt = CurrentMemoryContext` (explain_redact.c:144) and hands that same context to all three tables as `hash_ctl.hcxt` (:154, :160, :166). dynahash frees a table by deleting its context outright:

```c
/* src/backend/utils/hash/dynahash.c, hash_destroy() */
    /* so this hashtable must have its own context */
    Assert(hashp->hcxt != NULL);
    ...
    MemoryContextDelete(hashp->hcxt);
```

The comment states the precondition this code violates. `explain_redact_destroy()` (explain_redact.c:183-192) therefore deletes the caller's context on the first `hash_destroy(ctx->oid_map)`, then dereferences `ctx->local_map` and `ctx->col_counters` out of freed memory, then writes three NULLs into it. In a cassert build the freed region is clobbered with `0x7F`, making the `Assert(hashp->alloc == DynaHashAlloc)` on the second call the likely crash site. If the caller's context is the per-query context, everything else allocated there goes with it.

Nothing calls it: there is no caller in the tree, and none of the six SQL wrappers in the test module uses it — they all reset or delete their own `work` context instead.

Fix: give the context its own child to own. Create `ctx->cxt` as `AllocSetContextCreate(CurrentMemoryContext, "explain redact", ALLOCSET_SMALL_SIZES)`, allocate the `RedactCtx` and the tables in it, and make destroy a single `MemoryContextDelete(ctx->cxt)` with no `hash_destroy()` calls. The design's "freed by the caller's reset" property survives, because the child dies with its parent. Whichever shape is chosen, the entry point needs a test — an exported function with no coverage is how this survived.

## Where a returned name lives

`explain_redact_name()` returns two different kinds of pointer. The redacted branch returns `entry->name` (explain_redact.c:404-410), interior to a hash entry, valid as long as `ctx->cxt` lives. The exempt branch returns whatever `redact_real_name()` just allocated (:391-397) — `get_rel_name()`, `get_func_name()`, `get_opname()`, `get_collation_name()` and the two `pstrdup()` cases all allocate in `CurrentMemoryContext` *at call time*, which need not be `ctx->cxt`.

For the intended callers this bites. The design has the `RedactCtx` in `estate->es_query_cxt` while deparse runs in shorter-lived contexts; a name retained across a reset of the inner context then dangles if and only if the object was exempt. That is the worst shape for a defect, because it depends on catalog state rather than code path and will not reproduce against a fixture schema whose objects are all user-schema. The header comment (explain_redact.h:86-89) covers nullability and error behaviour and says nothing about lifetime.

The same branch allocates per call. `redact_is_exempt()` runs before the cache lookup, so every reference to the same object repeats the namespace lookup and `get_namespace_name()` (:307) returns a fresh copy of the schema name that is never freed. A plan naming one relation from twenty sites pays twenty syscache probes and twenty namespace-name allocations in the caller's context.

Both fall out of one change: look up `oid_map` first and run the exemption test only on a miss, storing the real name in `entry->name` on the exempt path without touching `ctx->counter[kind]`. Exempt objects still consume no counter, so the numbering-stability property the comment at :387 protects is preserved; names always come from `ctx->cxt`; and the namespace lookup happens once per object instead of once per reference. Real names are `NameData`, so they fit `name[NAMEDATALEN]` exactly.

`ctx->allow_schemas` is stored by reference (:145) with no copy into `ctx->cxt`, so the list has to outlive the context. Worth stating in the header, since the natural caller builds it from a GUC parse whose lifetime is not obviously longer.

## The column recursion is safe; the name it builds is not the documented one

The specific worry — `explain_redact_local()` holding `entry` across the recursive `explain_redact_local(ctx, REDACT_ALIAS, scope, 0)` at :461, which does `HASH_ENTER` on the same table before :463 writes through `entry` — does not hold. `expand_table()` in dynahash.c splits a bucket by rewriting `->link` pointers in place; elements come from element blocks and are never copied or moved, and `dir_realloc()`/`seg_alloc()` touch only the directory and segment arrays. `entry` stays valid across the inner insert. The two keys also cannot alias, `kind` differing, so the `snprintf` source and destination are distinct entries.

The prefix is wrong. The qualifier comes from `REDACT_ALIAS`, unconditionally, so a column pseudonym is always `aN_cM`:

```
columns_qualified_per_relation -> {a1_c1,a1_c2,a2_c1,a2_c2}
```

Four places specify `tN_cM`: explain_redact.h:7, the enum comment at :51, the API comment at :98-99 ("qualified by the owning relation's pseudonym (`t1_c3`)"), and design §3 / FR-12. As written the function cannot produce that form — the column key is a range-table index while the relation pseudonym is keyed by OID, so there is no path from one to the other without a caller supplying the relid. The expected output pins `a1_c1` and its comment defers the linkage to T07/T08, which means `explain_redact_local()` will have to change. Until then the header describes output the code cannot emit, and a reviewer auditing T07's call sites against the header would be auditing against the wrong contract.

This feeds a coverage gap. The FR-41 assertion (sql/test_explain_redact.sql:24) applies `^[a-z]+[0-9]+$` to the nine OID-keyed kinds. `a1_c1` fails that regex, and none of the eleven locally-keyed kinds is checked against it. Either FR-41 needs an explicit carve-out for the composite form or the format needs to change; either way the assertion should cover every kind rather than a third of them.

## Ruled out by inspection

`snprintf` truncation into `name[NAMEDATALEN]` is unreachable: the longest OID-kind pseudonym is a 4-character prefix plus an `int` (15 bytes) and the longest column form is a 12-byte alias plus `_c` plus an `int` (24), both well inside 64. The counters are `int` and advance once per *distinct* object in one plan, so overflow needs 2^31 distinct objects; the same bound covers `++colent->next`. Syscache references in `redact_object_namespace()` and `redact_real_name()` are released on every path that takes one, and the only error that can intervene is an OOM inside `pstrdup()`, where `CurrentResourceOwner` releases the reference at abort. `get_rel_namespace()`, `get_func_namespace()`, `get_namespace_name()`, `get_rel_name()`, `get_func_name()`, `get_opname()` and `get_collation_name()` all return `InvalidOid`/`NULL` rather than erroring on a missing OID, so the header's "never raises an error" claim holds and FR-60's fail-closed path is real. The uninitialized `HASHCTL` is the tree's own idiom; `hash_create()` reads only `keysize`, `entrysize` and the flag-guarded fields.

The regression test's placement in the `explain` parallel group (parallel_schedule:126) is safe: the two GUCs it sets are session-local, the schema name is unique, every table it reads is its own, it `ANALYZE`s explicitly so plan choice does not depend on autovacuum timing, and `DROP SCHEMA ... CASCADE` removes all 12 objects it created. The group holds 16 tests against `--max-concurrent-tests=20`.

## Four fixtures pass without reaching the path they name

The positive control (explain_redact.sql:331-348) groups by fixture and reports `'ok: ' || count(*)`, so a fixture passes when *any* marked identifier appears anywhere in its output. Replacing the count with `string_agg` of the identifiers shows which fixtures are carried by their table and column names alone:

| Fixture | Identifiers found | Named path present? |
|---|---|---|
| FR-16 index name (:249) | `zsec_customers, zsec_ssn` | no — plan is a Seq Scan |
| FR-20 user collation (:259) | `zsec_customers, zsec_ssn` | no — `COLLATE` folded away |
| FR-46 subquery output name + alias (:274) | `zsec_customers, zsec_ssn` | no — subquery flattened |
| FR-93 composite field assignment (:297) | `zsec_customers, zsec_ns` | no — field name not printed |

The plans:

```
FR-16   Seq Scan on zsec_customers             -- zsec_idx_ssn never named
FR-20   Filter: ((zsec_ssn)::text = 'x'::text) -- zsec_coll absent
FR-46   Seq Scan on zsec_customers             -- zsec_sub / zsec_out gone
FR-93   Update on zsec_ns.zsec_customers
          ->  Seq Scan on zsec_ns.zsec_customers
                Output: 'x'::text, ctid        -- zsec_fld_ssn absent
```

FR-16 is the most consequential. With 20 rows the planner never chooses the index, so the index-name emission site is not executed at all, and after inversion this fixture will report "index names are redacted" having never printed one. `SET enable_seqscan = off; SET enable_bitmapscan = off;` around a standalone assertion — the shape the FR-92 block already uses for `constraint_exclusion` — yields `Index Only Scan using zsec_idx_ssn on zsec_customers`.

FR-20's `COLLATE` sits on the Var, where `eval_const_expressions` absorbs it into the operator's `inputcollid` and no `CollateExpr` survives to deparse. On the constant it survives: `WHERE zsec_ssn < ('x' COLLATE zsec_coll)` gives `Filter: (zsec_ssn < 'x'::text COLLATE zsec_coll)`. The FR-98a sort-key fixture does reach a collation-name site, so this entry is redundant as well as misleading.

FR-46's subquery needs `OFFSET 0` to survive flattening — the trick the file already uses two sections later for the VALUES negative control. With it: `Subquery Scan on zsec_sub / Filter: (zsec_sub.zsec_out = 'x'::text)`. Without it the fixture reproduces FR-10 and FR-12 and nothing else, which matters because this is the entry the file's own comment cites when withdrawing the VALUES fixture ("which the subquery output name + alias fixture already covers").

FR-93's assignment case has no reachable shape I could find. Assigning from a column rather than a constant, and adding `RETURNING`, both still print only the scan's output list; the field name reaches output through a *read* (`(zsec_comp).zsec_fld_ssn` in a Filter), which the "composite field select" and "whole-row field reference" fixtures already cover. Converting it to a documented negative control, as the VALUES case was, records the fact instead of hiding it behind a pass.

Less severe, same shape: the FR-46 join fixture (:281) uses aliases `a` and `b`, which carry no marker, so a leaked join-RTE alias would be invisible to the detector. The FR-92 join fixture already uses `zsec_ja`/`zsec_jb`.

The class fix is to make each assertion name its target. A fifth column on `zsec_fixtures` holding the identifier the fixture exists to produce, asserted against the detector's result, turns all four of these red and catches the next one at the moment it is written.

## What the grep cannot see

Values that are not text are the first blind spot. The `zsecdata-` convention makes stored strings self-identifying, but `zsec_bal numeric` and `zsec_when timestamptz` cannot carry a marker, and the value-marking assertion (explain_redact.sql:216) only checks `zsec_ssn`, the two composite fields and the enum. The FR-98d fixture is where that surfaces: `WHERE EXTRACT(year FROM zsec_when) = 2020` deparses to `Filter: (EXTRACT(year FROM zsec_when) = '2020'::numeric)`, and the detector reports `zsec_customers, zsec_when`. Neither the field label nor the constant — the two things the fixture's note names — is observable by this mechanism. Assert on the plan text for this one, as the `[C]` probes do, or narrow the note.

Case is the second. Both detectors are case-sensitive (explain_redact.sql:131, 002_redact.pl:65). A marked value routed through `upper()` reaches the plan as `'ZSEC_VAL_SECRET'` and the detector reports only the table and column. The fixture data is lower-case today, so this is latent — but the inverted assertions from T04 onward are where it bites, because a leak that arrives upper-cased reads as clean. Adding the `i` flag to `regexp_matches` and `/i` to the Perl match closes it.

Escaping does not break it. The same fixture through all four formats returns the same five identifiers in text, JSON, XML and YAML: `zsec_` and `zsecdata-` contain no character that `escape_json`, the XML escaper or `escape_yaml` touches, and no format wraps long lines, so an identifier is never split across a boundary the line-joining detector would miss. That property is load-bearing for standing criterion 2 and nothing in T01 pins it — every fixture and every `zsec_leaks()` call site runs text format.

`zsec_leaks()`'s default `explain_opts` is `'REDACT'` (:106), an option that does not exist until T04. Every current call site passes options explicitly, so the default is dead code that errors rather than degrading for the first caller who omits the argument. The task plan's §3 block also calls this function `redact_leaks()`.

## Marking discipline runs before half the schema exists

The object-marking assertion (explain_redact.sql:171-211) is the mechanism §2.1 leans on to make the detector sound, and its comment claims "every object in the schema actually carries the marker". It runs at line 171; `zsec_fixtures` is created at line 232 with columns `fr`, `note`, `opts` and `qry`, none marked and none visible to the check. Harmless in itself — no fixture query touches that table — but the stated invariant is false, and anything added after line 171 is unchecked by construction. Moving the assertion past the last `CREATE`, and marking those four columns, restores it.

Both discipline queries omit `pg_proc.proargnames`, which is the one catalog the current fixture set depends on: FR-94's named-argument label `zsec_arg` is marked by hand and enforced by nothing. `002_redact.pl`'s version (002_redact.pl:137-169) does not have the ordering problem and adds `pg_trigger`, but inherits that omission.

## auto_explain: `Query Text` satisfies the assertion before the plan does

auto_explain emits `Query Text` in every record, so the statement's own text is in the log before any plan property is considered. Three assertions match against the whole log and are satisfied by that alone:

- 002_redact.pl:234-236 — `ok(scalar(@trig_leaks) > 0, "FR-17: detector fires on the trigger section")`. The query text contains `zsec_customers`, so the count is non-zero whether or not the trigger section was emitted. Its diagnostic output does list `zsec_plaintrig` and `zsec_ctrig`, so the section is in fact present — but the assertion never checks that.
- 002_redact.pl:400-402 — `grep { /zsec_elem|zsec_attr/ } @xml_leaks`. Both names are in the query text, so this passes whether or not the XML construction names reach the plan.
- 002_redact.pl:421 — `like($log, qr/zsec_ssn/, 'FR-98d: IS NORMALIZED expression is logged today')`. Same; the Filter does read `(zsec_ssn IS NFC NORMALIZED)`, so anchoring on that costs one regex.

Uniform fix: match the specific property line — `qr/Trigger zsec_plaintrig/` two assertions earlier already does — or strip through the `Query Text` line before calling `leaked()`.

## The libxml gate is always false; the ICU gate is unnecessary

```perl
my $has_libxml = $node->safe_psql('postgres',
    "SELECT count(*) > 0 FROM pg_proc WHERE proname = 'xmlelement'") eq 't';
```

`xmlelement` is grammar, not a function; `SELECT count(*) FROM pg_proc WHERE proname='xmlelement'` returns 0 on every build. `$has_libxml` is therefore always false, the FR-95 block skips unconditionally, and because a TAP skip counts as a pass the suite reports 24/24 with FR-95 permanently unverified. The task plan's note — "those fixtures live in the TAP test so they skip visibly rather than passing vacuously, and CI must include a build with both" — describes an outcome this gate cannot deliver. `$ENV{with_libxml}` is exported by both build systems for exactly this; `xmlcomment` is a real function if a catalog probe is preferred.

The ICU gate (002_redact.pl:405-413) errs the other way. `IS NORMALIZED` is implemented in `src/common/unicode_norm.c` and needs no ICU — on this build `SELECT zsec_id FROM zsec_customers WHERE zsec_ssn IS NFC NORMALIZED` plans and prints `Filter: (zsec_ssn IS NFC NORMALIZED)` — so a build without ICU collations would skip an assertion that would have run. The `current_setting('server_version_num')::int > 0` conjunct is always true.

## The tripwire verdict accepts any error

`zsec_t02_verdict()` (sql/test_explain_redact.sql:170-188) derives "tripped" from `EXCEPTION WHEN others` without inspecting the error. Any failure inside `test_redact_tripwire()` — an unrelated `elog`, an OOM, a future signature change — reads as a successful trip, and on a cassert build `should_trip` is true, so the test goes green either way. The surrounding construction is the right idea: comparing what happened against what this build should do is what keeps the expected output identical across cassert and non-cassert builds. It needs the error identified, via `SQLERRM` against `'redaction leak at test site%'` or a `SQLSTATE` check.

## The exemption boundary

`pg_catalog` is compared by OID against `PG_CATALOG_NAMESPACE`, which is exact. `information_schema` is compared by string (explain_redact.c:311-312), and PostgreSQL pins no OID for it, so the exempt set follows whatever schema currently holds that name. `ALTER SCHEMA information_schema RENAME TO ...` followed by `CREATE SCHEMA information_schema` puts a user schema inside the exempt set, and every object in it then prints in full under redaction. The action is privileged, which is why this is a posture note rather than a vulnerability, but it is the one place where the fail-closed design is name-dependent; resolving the OID once per context at least narrows the window to the lifetime of one record, and the header should say the exempt set depends on schema naming.

The allowlist is compared with `strcmp` against the raw list element (:314-318), so exemption depends on the list already being normalized the way the catalog stores names. The test wrapper uses `SplitIdentifierString`, which downcases unquoted identifiers correctly; the T04 GUC path needs to use the same, or `redact_allow_schemas = 'MySchema'` will silently fail to exempt `"MySchema"`.

## Build registration and a SQL-callable crash

`contrib/auto_explain/meson.build:29-32` lists TAP tests explicitly and names only `t/001_auto_explain.pl`, so `002_redact.pl` runs under `make check` (where `TAP_TESTS = 1` globs `t/*.pl`) and never under meson. The task plan's claim that the FR-29 fixture "needs no build changes" holds for the Makefile, where `EXTRA_INSTALL = contrib/pg_overexplain` is already present, but not for meson. Everything else is registered in both: `explain_redact.c` in `src/backend/commands/Makefile` and `meson.build`, the test module in `src/test/modules/Makefile` and `meson.build`, the regression test in `parallel_schedule` (which meson reads, so one registration covers both), and the eight new typedefs in `typedefs.list`. No build artifacts or stray files are staged, and the module's `.gitignore` matches the tree's convention.

The test module segfaults the backend on a NULL array element. `deconstruct_array` is called with a nulls array in both sequence functions (test_explain_redact.c:104-106, :168-174) and the result is never consulted, so a null Datum reaches `TextDatumGetCString`:

```
postgres=# SELECT test_redact_oid_seq(ARRAY['relation',NULL], ARRAY[1,2]::oid[]);
server closed the connection unexpectedly
```

`STRICT` guards a null *array*, not null elements. An `array_contains_nulls()` check on each input with an `elog(ERROR, ...)` is two lines.
